## Existing, unchanged

- `GET /api/v1/certifications[?category=...]`, `GET /api/v1/certifications/{certificationId}` and corresponding `/api/v1/hobbies` routes return the existing enum-category catalog shapes.
- `GET /api/v1/players/certifications`, `POST/PATCH/DELETE /api/v1/players/certifications/{certificationId}`; equivalent hobby routes retain catalog-ID semantics. A player record is a self-reported possession, **not** official acquisition verification.
- `GET/POST/PATCH/DELETE /api/v1/players/categories/{kind}` manage personal categories (`kind=CERTIFICATION|HOBBY`). `PATCH /api/v1/players/categories/{kind}/items/{itemId}/personal-category` uses **catalog** `certificationId`/`hobbyId`, not an owned-row ID. Deleting a category detaches its assignments, not the owned records.
- Dates follow `docs/contracts/common/date-validation-contract.md`: certification `acquiredDate`/`expiresDate`, hobby `startedOn` are optional ISO calendar dates in MySQL DATE range; on legacy PATCH, omitted/null keeps the saved date. Invalid dates return problem 400 before mutation. Existing domain errors and authentication rules remain.

## Additive API (implemented in source; deployment not yet verified)

| Purpose | Proposed route | Notes |
| --- | --- | --- |
| My selectable categories | `GET /api/v1/players/categories/{kind}/owned` | Only system/official groups with at least one owned item plus all personal categories, including empty ones; server-owned distinct query, not a page-derived calculation. `Category {id,code,name,source,kind}`; `source=OFFICIAL` code `HRDK:{majorCode}:{minorCode}`. |
| Public groups | `GET /api/v1/catalog/{kind}/categories` | `Category {majorCode,majorName,minorCode,minorName,source}[]`; certification provider hierarchy plus LEGACY; hobby enum as single level. Legacy enum `category` remains separate. |
| Search/page/details | `GET /api/v1/catalog/{kind}/items?q=&majorCode=&minorCode=&page=&size=`, `GET /api/v1/catalog/{kind}/items/{catalogItemId}` | `PageResult {items,page,size,totalElements,totalPages}` and `Item {ownedItemId,catalogItemId,name,category,source,sourceCode,majorCode,majorName,minorCode,minorName,issuer,administeringAgency,detail,detailStatus,sourceUrl,fetchedAt,owned}`. Page zero-based; default size 20, maximum 100; name then ID sorting. `majorCode=LEGACY` selects legacy certifications. Hobby has no minor category. `ownedItemId` is null when not held; `owned` uses authenticated current-player membership; no private hobby in public results. |
| Catalog acquisition | Existing `POST /api/v1/players/{certifications|hobbies}/{catalogItemId}` | Opens a form on double-click; only POST saves. Existing 409/ownership behavior and paths stay. |
| Private hobby | `GET/POST /api/v1/players/hobbies/private`, `GET/PATCH/DELETE /api/v1/players/hobbies/private/{ownedItemId}` | No global Hobby row. `POST {name,detail?,proficiency?,status?,startedOn?,personalCategoryId?}` defaults proficiency 0 and status ACTIVE, returns 201 + Location. `PATCH` accepts the same optional fields; omitted/null retains name/detail/proficiency/status/startedOn, while explicit `personalCategoryId:null` clears that assignment. `GET` list returns `Info[]`; all item calls return `Info {ownedItemId,catalogItemId:null,source:"PRIVATE",name,detail,proficiency,status,startedOn,personalCategoryId}`; delete 204. Private ID cannot be passed to legacy catalog routes. |

Private ownership responses distinguish `ownedItemId` (player row), `catalogItemId:null`, and `source:PRIVATE`. The legacy personal-category assignment path remains catalog-ID-based; private assignment is the owned-ID-specific PATCH field with server-enforced ownership and kind checks. A category foreign to the current player and an item foreign to the current player must not succeed. New endpoint errors use existing problem/error-code conventions: invalid input/date 400, unauthenticated 401, absent/foreign owned item 404, duplicate private normalized name 409 (`PLH-409-DUPLICATE-PRIVATE`). Name strips outer whitespace, must contain 1–60 Unicode code points; case-insensitive normalized duplicates per player are disallowed by a DB unique constraint. Repeating POST yields 409, not a second item: GET the existing entry or PATCH by `ownedItemId`; after POST succeeds but a later PATCH fails, retry PATCH only. Existing catalog-id POST→PATCH behavior is unchanged. `startedOn` uses the #395 optional date rule and invalid date returns problem 400.

Official certification scope is HRDK-managed national qualifications only, sourced from the official listing and per-item information, with stable provider/source code, major/minor source codes and labels, administering agency distinct from issuing authority (`issuer:null` when unverified), plain-text detail, source URL, fetched time, and BASIC/COMPLETE detail status. Legacy entries lacking provider classification stay identifiable as LEGACY/OTHER; their existing enum remains. `OfficialCertificationImportCommand` accepts an operator-prepared normalized JSON manifest (`complete`, `expectedCount`, `fetchedAt`, `listingSourceUrl`, `pages:[{page,pageSize,returnedCount,totalCount}]`, `items:[{sourceCode,name,issuingAgency,majorCode,majorName,minorCode,minorName,administeringAgency,detail,detailStatus,sourceUrl}]`), defaults to dry-run and applies only with `--catalog.hrdk.apply=true`. Invoke the jar with `--spring.main.web-application-type=none --catalog.hrdk.import-file=/path/to/verified-manifest.json`; inspect dry-run first. The manifest must have contiguous page evidence, every source code, real official origin URLs and verified original semantics; invalid/incomplete input aborts without deleting existing definitions. It is not a live provider fetch or a FE-triggered operation. The HRDK item-information API at `https://www.data.go.kr/data/15003003/openapi.do` documents `jmCd` and `ServiceKey`. The unauthenticated HRDK MCP supports bounded searches and item display but did not provide a complete paginated source with original major/minor codes; it is not treated as a full catalog. No actual complete source or credential has yet been verified, and CI fixtures are synthetic. Source/data ready remains **false**. Public hobby recommendations are service-curated, not official, and have no reward side effect.
