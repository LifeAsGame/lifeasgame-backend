# Portfolio demo run contract — READY

`templateVersion: portfolio-v1`; `implementationReady: true`; `runtimeReady: true` (19081, 2026-10-08 KST).
This contract applies only to the explicitly enabled, loopback-bound 19081 preview. Success bodies use the existing `ApiResponse` envelope (`result` contains the shapes below); errors use the existing `application/problem+json` shape with `status` and `code`. Times are UTC ISO-8601 instants. No credential or one-time code is stored in this document.

## Session and authentication

1. `GET /api/v1/demo/bootstrap` (anonymous, `credentials: include`) creates a short-lived server-owned browser proof. Response: `{templateVersion, proof, expiresAt}`. The server also sets an HttpOnly, SameSite=Strict, path `/api/v1/demo` proof cookie. `proof` is sent in the `X-Demo-Proof` header only for a start request. An unrelated browser cannot retry a start from another browser.
2. `POST /api/v1/demo/runs` (anonymous, proof cookie, `X-Demo-Proof`, `Idempotency-Key: <new UUID>`, empty JSON body) explicitly starts a **new** run and returns HTTP 200. Repeating the same key and proof returns the same `{runId, templateVersion, status, createdAt, expiresAt, failureCode, actors, scenarios}`. A different key means a new login/run and closes the prior run from this browser's manager cookie. A run-management HttpOnly cookie is issued. The response never includes actor credentials. No ordinary login/register/refresh call starts a run.
3. `GET /api/v1/demo/runs/current` (management cookie) and `GET /api/v1/demo/runs/{runId}` (management cookie, exact current ID) return the same run view. Poll while `PROVISIONING`; only `READY` permits an actor token. `FAILED` is recoverable through `POST /api/v1/demo/runs/current/retry` with the same management cookie. A retry resumes the **same** run and must not duplicate seed effects.
4. `POST /api/v1/demo/runs/current/actors/{actor}/activate` (management cookie; `actor` is one of the returned server-owned actor names) returns `{runId, actor, accessToken, refreshToken, userId, playerId}`. Roles switch within the same run without resetting progress. Store each actor's tokens separately. Existing `POST /api/v1/auth/refresh` may renew an actor token but does not create a run; expiry/closure still invalidates it. Discard prior actor tokens, queries, WebSocket subscriptions, and cached IDs on a new run.
5. `POST /api/v1/demo/runs/current/peer-links` (management cookie) returns `{code, expiresAt}` for the chat peer only. `POST /api/v1/demo/peer-links/redeem` with `{code}` in an independent browser returns the peer token pair and its run/actor IDs. A code is single use and expires after five minutes. Redemption does not create a run or grant management rights. Do not put the code in a URL or logs.
6. `POST /api/v1/demo/runs/current/close` (management cookie) closes the run. A closed or expired run denies its actor JWTs on HTTP and STOMP CONNECT/SEND/SUBSCRIBE; refresh also fails. Default TTL is 24 hours, configurable on the preview server.

Statuses are `PROVISIONING`, `READY`, `FAILED`, `EXPIRED`, and `CLOSED`. A run view contains `runId`, `templateVersion`, `status`, `failureCode` (null except FAILED), `createdAt`, `expiresAt`, `actors: ["explorer","seller","journey"]`, and `scenarios` (codes, price/quantity, and target IDs). Target IDs are zero while preparation is incomplete; use them only at READY. A failed run has stable `failureCode: "DEMO-PROVISION-FAILED"`, not a stack trace. Errors: `400 DEMO-INVALID-REQUEST`, `401 DEMO-PROOF-INVALID` or `DEMO-SESSION-INVALID`, `403 DEMO-ACTOR-FORBIDDEN`, `404 DEMO-RUN-NOT-FOUND`, `409 DEMO-NOT-READY`, `410 DEMO-RUN-EXPIRED`, `429 DEMO-CAPACITY-EXCEEDED`, and `503 DEMO-DISABLED`. The server controls all actor IDs and seed IDs; no start, switch, or peer-link endpoint accepts a Player ID or seed path.

At READY the `scenarios` object has `marketplace: {buyer:"explorer", seller:"seller", itemCode:"IT_RECORD_CRYSTAL", price:25, quantity:1, listingId}`, `recordReward: {actor:"explorer", firstQuestCode:"Q_RECORD_FIRST_TRACE", mailQuestCode:"Q_ADVENTURE_PREPARATION", recordCountForMail:3}`, `journey: {actor:"journey", routeCode:"ROUTE_BACKEND_DEVELOPER_START", firstQuestCode:"Q_DEV_DEFINE_BACKEND_GOAL", roleId, projectLifeLogId}`, and `chat: {actorA:"explorer", actorB:"seller", channelId}`. The Route ID and current Step ID come from existing `GET /api/v1/quest-routes` and `GET /api/v1/quest-routes/my/{routeId}` after actor activation. Success statuses: all demo GET/POST calls return 200 except close (204); the product endpoints retain their own established statuses.

## Fixed starting content

The run has the minimum three actors: `explorer` (buyer, record/reward, chat A), `seller` (market seller, chat B), and `journey` (backend developer). The only shared catalog definitions are the currently installed Quest, Route, Achievement/Title, and Item definitions. All mutable balances, inventory, listings, records, and chat are per run.

| Flow | `READY` starting condition | Visitor action |
|---|---|---|
| Marketplace | `explorer` has 100 GOLD available. `seller` owns one unbound `IT_RECORD_CRYSTAL`; its OPEN listing is 1 item for 25 GOLD. No reservation/trade exists. | As explorer, reserve and purchase the returned listing ID. Read both wallets, inventories and trades by switching actors. |
| Record/reward | `explorer` has accepted `Q_RECORD_FIRST_TRACE` and `Q_ADVENTURE_PREPARATION`, both at progress 0; no LifeLog, achievement/title grant or reward mail has been consumed. | Save one `COLLECTION/QUICK_NOTE` through `POST /api/v1/lifelogs/quick-record` with `Idempotency-Key` to complete the first-record Quest and grant. Save two more distinct records to complete the existing three-record Quest; its product reward creates the claimable `IT_RECORD_CRYSTAL` mail. Claim through the existing mailbox API, then inspect growth, inventory, achievements and titles. The first-record Quest grants EXP only, so the third record is required for Item mail. |
| Backend journey | `journey` has active `ROLE_BACKEND_DEVELOPER`, a PROJECT example LifeLog, and has **not** selected `ROUTE_BACKEND_DEVELOPER_START` or accepted/completed its Quest. The Route has seven active steps. | Select the Route with that Role, accept `Q_DEV_DEFINE_BACKEND_GOAL`, link evidence, complete, and explicitly advance the first step. Continue later steps if desired. |
| Friend chat | `explorer` and `seller` are friends with an empty FRIEND channel. No automatic live response. | Connect two real sessions, send, mark read, disconnect/reconnect. Use existing REST history/read and STOMP `/ws`, `/topic/social/chat/{channelId}`. |

All IDs in `scenarios` are resolved from the run, never guessed. Demo actors may read or mutate only resources owned by their run. Public marketplace search excludes other runs and ordinary accounts; ordinary accounts cannot find or operate demo assets. Same-run actor switching is not a new login.

## Server limits and cleanup

Default TTL: 24 hours. Preview configuration sets ceilings of 20 active runs, 30 creations per UTC day, and 500 total retained runs; all are configurable. At capacity the start returns 429 without provisioning anything. `scripts/portfolio-demo-cleanup.py` defaults to a dry run and reports only expired/closed run IDs and counts. `--apply` prunes expired proof and peer-link rows for that scope. Run/actor revocation rows and domain accounts, balances, inventory, listings, trades, chat, receipts, and outbox history remain physically retained, so reaching the total cap requires a separate reviewed archival policy. No global DB reset or prefix-based deletion is part of this contract.

One disposable run reached READY and completed the initial wallet/record checks, marketplace trade, three-record reward mail claim, journey step-one advance, peer-link chat send/read, and close/token revocation. A separate 19082 stage verified two-run ownership isolation, ordinary-account exclusion, replay, and a fresh run after closing the previous one. The existing 19081 accounts and the separate 19080 and 13005 previews remained available. The disposable 19081 run is CLOSED; its audit and product rows are retained by the cleanup policy above.
